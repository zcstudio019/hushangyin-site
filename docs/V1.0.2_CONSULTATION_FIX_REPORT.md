## 1. 真实故障原因

### 已复现的故障链

本次检查发现两个同时运行、界面相似但行为不同的入口：

| 检查对象 | 修复前实际结果 |
|---|---|
| 3000 | Node/Next.js，返回 `/_next/` 资源；没有用户描述的两段演示提示；本地测试标识存在；咨询未禁用 |
| 8080 | Python `http.server`，返回旧 `contact/index.html`，加载 `/assets/site.js`；存在两段原样演示提示 |
| 本地配置 | DATABASE_URL/SESSION_SECRET/RATE_LIMIT_SECRET已配置，CONSULTATIONS_ENABLED=true、LOCAL_TEST_MODE=true |
| PostgreSQL | 现有 `127.0.0.1:55432` 正常，Prisma连接 `hushangyin_local` 成功，版本18.6 |

具体代码：

- 旧 `contact/index.html:1` 的静态表单底部硬编码“演示版本尚未启用客户信息接收服务，页面不会发送或储存您的填写内容。”
- 旧 `assets/site.js` 中 `consult-form` 的submit监听器执行 `preventDefault()`，验证后直接把feedback改成“当前为演示版本，尚未启用安全接收接口，因此没有发送或保存您的咨询信息。”；它没有调用fetch/API。
- 3000的 `src/components/forms/ConsultationForm.tsx` 已经调用真实 `/api/consultations/`；服务端经 `consultationAvailable()`、Zod、限流进入 `createConsultation()`，Prisma事务保存leads和consents。修复前3000返回页面不加载旧site.js，因此不是该React表单内仍有演示实现。

用真实浏览器打开当时仍在运行的8080，填写全新虚构信息后点击提交，逐字复现了演示提示，网络POST计数为0。证据为 `test-results/v102/before.json`、`before-legacy.png`。旧Python进程日志也记录了对 `/contact/`、`/assets/site.js` 等旧资源的访问；检查时有浏览器进程与8080保持连接。

此前验收验证了Next测试进程、3000和数据库，却保留了8080旧预览，没有统一入口或验证旧链接的去向。于是“新平台测试通过”与“访问旧入口仍只能演示”可以同时发生。这是上一轮入口治理和验收覆盖的遗漏。

原Quark标签页的URL无法通过当前内置浏览器连接直接读取，因此不把原标签地址声称为已读取事实；以上结论来自实际监听进程、两端HTTP响应、源码和8080真实浏览器复现，没有将问题猜测为缓存。

## 3. 修复结果

当前调用链：

`8080旧链接 → 307到3000 → React咨询表单 → 浏览器真实POST → 服务端同源/校验/开关/限流 → Prisma事务 → PostgreSQL leads + consents → 201 + reference → 前端成功提示 → 后台读取同一记录 → PATCH状态 → 刷新及数据库核对`。

`npm start` 和 `npm run dev` 均读取本地配置、固定当前项目目录及3000端口。在LOCAL_TEST_MODE=true且SITE_URL为本机3000时，8080只对GET/HEAD提供无缓存307，保留路径和查询参数；非读取方法不在旧入口收集资料。生产模式不启用该兼容监听。

3000当前返回版本头 `platform/1.0.2`，表单 `data-submission=api`，不加载旧 `/assets/site.js`。新前端成功提示为“咨询需求已成功提交，沪上银工作人员将与您联系。”，不承诺确定时效。

数据库不可用时API仍统一503、屏蔽内部异常；页面显示可理解的失败状态，保留填写内容供核实后重试，不显示成功。网络无法确认结果时仍显示“暂未确认是否提交”，避免错误断言已经保存或一定未保存。

隐私勾选、必要字段、8KB请求限制、持久化限流、事务防重、服务端权限和审计继续有效。原后台查询直接读取现有PostgreSQL，无Mock和内存替代。
