# GEO 内容审核权限与审核入口专项修复报告

日期：2026-10-30。项目：`D:\Codex\hushangyin-site`。环境：本地 Next.js 3000、既有 PostgreSQL 55432。未部署生产。

## 1. 实际故障原因

不是角色名称错误，也不是浏览器缓存导致权限丢失。原审核 API、审核中心和发布流程都存在，但历史导入内容遇到了“唯一审核人也是内容参与人”的职责死锁。

本轮实际登录本地管理员，并通过登录后的 profile、审核中心接口、代码及数据库交叉核对：

| 原账号非敏感标识 | 角色 | 审核权限 | 发布权限 |
|---|---|---|---|
| `cmvrsdpzy0000t1w4pb2wnprh` | SUPER_ADMIN / 超级管理员 | 有 | 有 |
| `cmvudx4dq0056t11gshj9efjx` | CONTENT_OPERATOR / 内容运营 | 无 | 无 |
| `cmvsyywro006bt1h0cnvqqvwv` | FINANCING_ADVISOR / 融资顾问 | 无 | 无 |

原60组FAQ均为待审核、版本1，其 authorId、editorId、importMetadata.importedBy 都是上述管理员；submittedById、submittedAt 为历史空值，不能伪造补填。示例FAQ为 `cmvtawqvq006kt1lo6pc45c16`。当前快照编辑人同样为原导入管理员。

原 `service.ts` 审核条件排除作者、编辑人和提交人。原权限映射又只有超级管理员有 content.review，所以该管理员有审核权限，却不符合本人内容的审核独立性要求；运营和顾问不能接替，合格独立审核人数为0。来源也全部为空，即使安排了审核人，仍须先补充真实核验来源。

原入口 `/admin/geo/reviews/` 能列出待审核FAQ；按钮位于具体内容详情中的工作流表单，并非另有一个未挂导航的审批系统。此前只提示再找一位超级管理员，缺少低权限审核员和按版本分配能力。前后端还分别计算自审条件，不利于定位具体阻塞原因。

会话每次从数据库读取当前角色、启用状态和会话版本；本轮真实管理员的登录ID与页面权限判定一致，审核员停用后的旧会话立即被拒绝，因此没有通过清缓存或更改角色名称来掩盖问题。

## 2. 本次实现

### 独立审核职责与正式授权

新增固定角色 `CONTENT_REVIEWER`（独立内容审核员），只包含原有 `content.read`、`content.review`。没有重建登录系统、用户表或权限体系，没有重命名原4种角色。

该角色不能创建/编辑内容、发布、下线、读取客户线索、管理员工、分配审核人或调用AI生成。原运营角色仍负责创建、编辑、补来源和提交，不自动获得审核权限；原顾问权限也没有变化。

超级管理员在原员工管理中正式新增或授权独立审核人员：

`/admin/settings/users/new/?role=CONTENT_REVIEWER`

页面只预选角色，不能凭URL直接授予权限。后端仍验证 users.create/users.update、roles.manage、当前密码重新认证及会话状态。授权记录 `USER_CREATE` 或 `ROLE_CHANGE`，并新增 `CONTENT_REVIEWER_GRANT` / `CONTENT_REVIEWER_REVOKE` 审计事件。本地初始凭据沿用原一次性15分钟流程，首次登录必须改密；未完成初始化不会成为合格候选人。

**没有自动提权现有内容运营或融资顾问，没有更改原管理员密码，也没有擅自保留实际的新员工账号。** 测试中正式创建的A/B账号已经按精确ID清理。真实审核岗位由负责人安排实际人员使用。

### 统一的版本参与人与审核资格判断

新增统一服务 `review-policy.ts`，详情页、审核中心和实际审核API使用同一规则：

- 权限必须包含 content.review，账号已启用并完成初始化。
- 排除原作者、当前编辑人、提交人、原导入人、本版本快照编辑人及本版本提交审计中的参与人。
- 不改原作者，不把历史NULL提交人填成其他员工，不修改旧审计来制造“独立”。
- 如果版本已经分配，只能由该合格审核人批准或驳回；其他人包括超级管理员也不能直接跳过分配。确需调整须正式重新分配并记录审计。
- 账号停用、权限撤销、版本变化或分配失效时拒绝审核。新增行锁将内容操作中的账号权限检查保持到事务提交，避免正常账号变更与审核交错时使用过期资格。

原 ContentReview 继续保存实际审核人、版本、决定、清单、原因和时间；没有第二套审批记录系统。未分配时，任何合格的独立审核人仍可按原流程审核，不强制所有内容都先走分配操作。

### 按固定版本分配审核人

超级管理员进入待审核内容详情，在“审核人分配 · 版本N”选择合格人员。新增权限 content.assign_review 仅授予超级管理员，服务端重新验证人员、版本及状态。

分配不等于通过，更不等于发布。修改、撤回、驳回或恢复生成新草稿版本后，原分配清除，记录 `CONTENT_REVIEW_ASSIGNMENT_INVALIDATED`；新版本重新提交后须重新分配。每次分配记录 `CONTENT_REVIEW_ASSIGN`，包含操作者、旧/新审核人、版本和时间。

没有合格人时明确显示“审核受阻”，提供正式新增独立审核员与原员工管理入口。不能选择参与人、已停用人员、尚未改初始密码的人员或无审核权限人员。

### 审核入口及具体阻塞提示

`/admin/geo/reviews/` 现在分为待审核内容、待发布内容、已审核记录、已驳回记录、全部审核历史，继续支持文章/FAQ筛选和分页。每项显示当前分配、合格人数、当前账号能否审核及具体引用缺项。

具体详情可查看完整正文、来源、修改记录和风险提示；“当前账号与版本权限判定”展开后显示内部用户ID、角色、审核/发布权限，以及作者、编辑人、提交人、导入人、快照编辑人的非敏感标识。

符合资格的审核员能看到“审核通过”和“退回修改”。引用缺失、格式不全、核验日期晚于今天或已经过期，均逐项说明；引用缺失时批准按钮禁用，服务端也拒绝伪造请求，但仍可按规则驳回并说明原因。来源格式通过不代表金融事实已被证明，仍需人工核验。

审核通过保持待发布，发布仍单独验证 content.publish 和该具体版本的通过记录。已发布内容修改后仍保留旧公开快照，新版本未通过不能替换；原公开FAQ路由及Sitemap机制沿用。

## 5. 接口

- 新增 `POST /api/admin/geo/{articles|faqs}/{id}/review-assignment/`，请求仅接受 revision、assigneeId（可空以解除分配）；需 content.assign_review、同源、有效登录和固定版本，沿用内容写入限流与4KB请求体限制。
- 沿用 `GET /api/admin/geo/reviews/`，支持 pending、ready、approved、rejected、history；待审核项返回权限原因和分配诊断，仍需content.read。
- 沿用 `POST /api/admin/geo/{kind}/{id}/workflow/` 的 approve/reject/publish/offline，增加统一参与人和指定审核人校验，未绕过原清单、来源、版本或发布权限。
- 沿用 `/api/admin/users/`、`/api/admin/users/{id}/` 正式授权新角色；没有匿名授权接口、默认审核员或前端直接写数据库。

## 8. 负责人现在如何操作

1. 以超级管理员进入新增独立审核员链接，填写实际人员资料，验证当前密码并正式授权；也可在原员工管理通过正式编辑授权另一位适当人员，不要给自己换角色来绕开独立性。
2. 安全交付本地短期初始凭据，让另一位人员完成首次改密。审核员不需要超级管理员权限。
3. 对历史FAQ先由作者撤回，补充真实可核验来源和必要修订，保存后重新提交；原作者和导入信息保持。
4. 管理员进入当前版本详情选择合格审核员，保存分配。新版本必须重新分配，不能复用旧审批。
5. 审核员从审核中心阅读全文、来源、风险，填写清单和说明后批准或驳回。通过后仍未公开。
6. 有发布权限的人在待发布页进入该版本，点击“发布到官网”。
